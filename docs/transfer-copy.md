# Copying files with Nearly

Use the installed Nearly application with WebView2 Runtime available. Connection credentials remain session-only. Saved bookmarks and folder correspondence do not require keeping a tab open. See the [r2.0 release notes](../.github/release-notes/r2.0.md) for settings compatibility and current verification limits.

## Same-pane Duplicate, Copy/Paste and Move

Remote Duplicate and same-server Copy/Paste use the advertised SFTP `copy-data` extension when available. File contents then stay on the server. Otherwise Nearly relays contents through one authenticated connection using a sliding window of at most thirty-two 32 KiB chunks. Server-side requests copy at most 4 MiB each. An explicit unsupported-extension response is remembered for that connection; failed or uncertain server-side copies are not automatically replayed. No remote shell command is executed.

Remote multi-item moves share one connection. Local and remote moves rename the selected root without inventorying descendants; moving a folder therefore does not read or follow its children. Source-root checks, cancellation and operation reservations remain in place. Existing ancestors are checked once per selection. Moves use standard SFTP v3 RENAME, whose contract rejects an existing destination, rather than the overwriting POSIX-rename extension; servers must implement that contract. A failed rename does not fall back to copying then deleting the source. Cross-filesystem moves can therefore still fail.

Same-pane copies create new destinations exclusively and refuse collisions. They check source metadata before copying and validate each parent path on its first use in the selection. Successful transfer/close acknowledgements complete a copy; no post-copy source metadata probe is performed. Copies are not snapshots of concurrently edited files, and external parent replacements are not rechecked within the selection. Failed or cancelled copies may leave partial new destinations. Only confirmed successful moves leave the cut clipboard; failed, uncertain and unattempted items remain. Refresh before retrying an uncertain result.

Remote regular files up to 256 KiB are copied in groups of at most four, including children within a selected folder. Larger files and directory creation remain sequential. The server-advertised handle limit can reduce the group width; an unavailable limits extension uses the bounded default, and a failed limits query falls back to one file. A reported limit below two file handles refuses copying. A group uses at most eight file handles and 1 MiB of relay payload in flight (excluding protocol framing and buffering).

A failed group stops further admission, settles all already started siblings, and reports every selected result in its original order. Cancellation stops new transfer stages and waits for admitted transfer/CLOSE requests to finish or reach their existing 15-second request timeout. This is a per-request limit, not a total cancellation deadline; handle cleanup can add a further wait. Acknowledged sibling successes remain successful. Partial or uncertain targets are retained; no failed mutation is replayed.

Same-pane copies show a byte bar for the current selected file, folder, or bounded group of small files, including local single-file copies. A separate overall count shows confirmed completed selections. Each selected folder uses its existing required inventory; Nearly does not scan every selected root in advance just to compute a grand byte total. The remote small-file group is labeled separately from a single current item. Its bar counts the group's acknowledged bytes, while a selected folder keeps its own aggregate byte count. The bar restarts when the next selected root or group begins, and keeps its byte value while each file is being finalized. Moves show stages and completed selection counts, without a byte percentage. A full byte bar means the data has been transferred, not that finalization or the operation has succeeded. Cancelled or failed copies retain the confirmed item count and an incomplete result, without a completed byte bar.

The existing upload/download staging and replacement behavior below is separate from same-pane copies. Generated fixture measurements and the limits of those measurements are described in [file-operation performance](file-operation-performance.md).
Drag local files or folders to the remote list, a remote folder row, or the remote tree. The centered confirmation captures the source, connection, and destination. Folders include their contents. Navigation after confirmation cannot redirect that operation. Remote items can likewise be dragged to the local pane to download copies.

For an existing file, choose Replace, Skip, or Keep both (rename). Apply to all covers matching conflicts in this operation only. Directories merge and retain unrelated children. A file/folder mismatch offers Skip or Keep both; it never recursively deletes an existing directory. Sources are retained.

Files are written to an exclusive staging sibling before publication. Nearly rechecks captured source and destination metadata. Unsupported replacement capabilities or changed targets fail without intentionally deleting the old file. Local overwrite conservatively refuses security metadata or encryption mismatches. Neither SFTP atomic rename nor Windows destination-path replacement supplies an atomic identity compare-and-swap: the final race with an independent external writer cannot be completely excluded. Refresh after a failure or uncertain acknowledgement before retrying. Owned staging files may remain after a lost connection.

The progress gauge counts acknowledged bytes across the whole transfer batch. Scanning, connecting, and conflict confirmation remain indeterminate. Finalization retains valid byte progress and is labeled separately; receiving all bytes does not confirm publication. Zero-byte work stays indeterminate until the authoritative outcome. Regular-file sizes must be available, and the complete inventoried batch must total no more than 9,007,199,254,740,991 bytes (about 9 PB), so byte counts remain exact in the interface. Larger or overflowing totals are refused before destination writes or Explorer descriptor publication; use smaller batches. Directories contribute zero bytes. Skipped file bytes are removed from the transfer plan, and empty or all-skipped batches complete only when the operation returns its result.

For Windows Explorer, hold the left button while dragging a remote item out of Nearly. The native provider advertises COPY and a bounded complete list of virtual file descriptors, then streams contents when the receiver requests them. Explorer manages its destination conflicts and any partial output. Nearly does not create an eager temporary copy tree. The provider refuses more than 10,000 entries, depth above 64, unsupported Windows names, or descriptor paths exceeding 259 UTF-16 units; bytes are read in bounded chunks. Cancelling or ending the operation releases its connection and session lease. A stalled asynchronous receiver has a timeout.

The interactive Windows drag loop runs on Tauri's UI thread; metadata and the separate SFTP connection remain on workers. OLE COPY status or a successful stream read alone does not establish Explorer output. External drag/drop cancellation with a short Escape tap and the latest menu/tree interactions in a real native UI remain unverified; see the [r2.0 release notes](../.github/release-notes/r2.0.md). The test harness stops before input when another window covers its owned Explorer destination.

On connection, trees expand toward the current directory and vertically reveal it after pending reads complete. Showing a tree reveals the current directory or its nearest rendered ancestor without opening collapsed descendants or navigating the other pane. Unrelated branches keep their own focus. Keyboard focus uses the normal visible focus ring. Confirmed successful operation cards disappear after five seconds. Cancelled downloads, including native Windows copies, also expire after five seconds; upload cancellations, other file-action cancellations, errors and partial outcomes remain until closed.

Qualification uses generated local files, mock browser RPCs, and localhost SFTP fixtures. Actual Explorer output must be checked separately from DOM routing and COM unit tests. No successful test implies qualification against a user's server, long-running stability, physical hardware gestures, or mixed-DPI/multi-monitor configurations. See the [r2.0 release notes](../.github/release-notes/r2.0.md) for the published qualification limits.
